`apps/web/src/components/TeamListCard.tsx` only strikes a player's name through on the INITIAL roster grid if a later (TWENTY_FOUR_HOUR or FINAL) LINEUP_CHANGE event's `body` contains the exact phrase pattern `Omitted from the NN — Name, Name.` (regex `OMITTED_NAMES` in that file — an em dash "—", not a hyphen, right after the number). Any other phrasing ("Name and Name have been omitted from the squad...") parses as plain text and silently never triggers strikethrough — no error, it just doesn't render struck-through.

**Why:** I once wrote a 24hr squad-trim update in narrative prose instead of this exact pattern; it posted fine and displayed as a normal update, but the promised strikethrough-on-the-initial-list effect (which the user specifically called out as a marketed feature: "Strikethrough shows who's been dropped — see every change at a glance") never appeared. The user had to ask what happened to it.

**How to apply:** whenever adding a TWENTY_FOUR_HOUR or FINAL LINEUP_CHANGE event that omits players from an earlier INITIAL list, lead the body with `Omitted from the NN — Name, Name.` (NN = total names in that team's INITIAL list for the game), matching the omitted players' names character-for-character against the INITIAL list (matching is case-insensitive but otherwise exact). Continue with any other narrative after that first sentence — the regex only needs the leading clause. Do this automatically, don't wait to be asked each time. See [[signings_general_news_rule]] for a similar "just apply this automatically" data-entry rule.

**Update (2026-09-04), confirmed preference:** for a FINAL update specifically, when the user supplies (or it's derivable from context) the actual full numbered squad — not just a prose description of what changed — write the body as the complete structured list in the same format as an INITIAL entry: `1. Name, 2. Name, ... 13. Name. Bench: 14. Name, ... 19./2X. Name.` followed by the `Omitted from the NN — ...` sentence. TeamListCard.tsx only renders the nice two-column starters/bench grid when it detects ≥10 "N. Name" tokens with a "Bench:" label (parseTeamList) — a prose-only body ("Fermor moves into the centres...") just renders as a plain paragraph instead. Told directly: "I like this style u did better with the full team listed in the final update" — after doing exactly this for two teams' FINAL updates unprompted (converting an earlier prose-only FINAL body into the full grid once the complete squad was known). Jersey numbers stay the player's own original squad number even when playing out of position (e.g. a bench player who moves into the run-on side keeps their bench number) — don't renumber to match the position. When cross-checking a supplied final squad against the original INITIAL list, list *every* player missing from that original count in the Omitted sentence (not just the newest one) — catches a real case where a reserve (Sebastian Su'a) had quietly not made the final 19 without ever being explicitly called "omitted."

**Update (2026-09-04), shipped feature — changed-player highlighting:** built and confirmed ("Perfect good work save this logic for all future") off the back of the full-grid preference above. `computeChangedNames()` in TeamListCard.tsx auto-highlights (heliotrope, bold) any player occupying a different slot on a 24hr/Final grid than on the INITIAL grid — no extra phrase needed in the body, it's derived automatically from parseTeamList's output on both bodies. Starters (1-13) are compared *by list order/slot*, not jersey number — number stays with the player through a position move (see above), so index is what actually encodes "which position." Bench is compared *by set membership*, not order — interchange order has no positional meaning, so an index compare would falsely flag everyone listed after whoever actually moved. Each stage (24hr, Final) is diffed independently against INITIAL, never chained stage-to-stage, so a Final that reverts a 24hr-stage change correctly stops flagging that player. No-ops safely (empty highlight set) when a stage's body isn't a full structured list. **How to apply going forward:** nothing extra to write — just keep supplying/entering the full structured squad per the update above, and the highlighting follows automatically. Don't invent a manual "changed:" phrase convention; the diff is computed, not declared.

**Update (2026-09-04), banned phrase — "remains in the reserves mix":** never write this for a 24hr update's surviving reserve(s); it reads oddly. "He should never say in the reserves mix. It doesn't really make sense. Just say it remains the one reserve." Use e.g. `<Name> remains the one reserve as <Team> trim their squad ahead of <Day>'s clash with <Opponent>.` when exactly one reserve is left (adjust to "the two reserves"/names if more than one remain) — corrected across four already-published 24hr entries (Cowboys, Raiders, Bulldogs, Broncos) that all had the old phrasing.

**Update (2026-09-04), standing instruction — NRLCentral tweet for FINAL team-list updates:** "Moving forward I will also need a NRL central tweet for the Team list changes" — clarified this is specifically **for the FINAL update** (not 24hr). Same tweet-drafting behavior [[news_article_workflow]] already applies to pasted articles — extend it to every FINAL LINEUP_CHANGE entry too, not just News items. Do this automatically after publishing a FINAL team-list update, without being asked each time: a short tweet-voice draft (quotes/figures fine, strictly from what was actually given — no inventing details not stated) covering the key changes (omissions, position swaps, bench moves), reply with it the same way a news-article tweet draft is given — never auto-post to X. Applies going forward from this point; not a request to backfill tweets for updates already entered before this instruction, though the Titans/Dolphins FINAL updates entered just before it were the first ones this was actually done for.

**Update (2026-09-05), corrected — tweet is changes-only, never the full roster:** "The tweet u send after the final team updates should not be the whole team list just the final updates." The published News/app body for FINAL is correctly the full structured grid (see the 2026-09-04 update above) — that full-grid rule is for the app body only. The tweet is a completely separate, shorter piece of copy: diff the FINAL body against the INITIAL body (same team, same game) and report only what actually changed — who's in/out and why (injury, form, etc. — pull the reason from the article's narrative text when available, e.g. "Leka Halasima (ankle) OUT"), any position swap, any bench reshuffle. If a side has zero changes to its starting 13, say that plainly rather than restating the unchanged lineup. Never re-list the full 13/bench/reserves in the tweet just because the app body has them.

Two more corrections from the same Warriors v Sea Eagles tweet, same session:
1. **Trace multi-stage position moves, not just the net in/out.** A player can shuffle position across INITIAL → 24hr → FINAL (e.g. named at fullback initially, moved to centre at 24hr, moved to wing at Final) — reconstruct and state the *whole* journey ("moves to wing from centre, after originally being named at fullback"), not just "now plays wing." The position label isn't in the app body's plain "N. Name" text — pull it from the Late Mail scrape's per-player `position` field (lib/lateMailParser.ts's `ParsedPlayer.position`) when available, or infer from [[nrl_jersey_number_positions]] jersey-number convention for a stage that predates the scraper.
2. **Don't present something already reported at 24hr as new Final-stage news.** "Leka Halasima (ankle) was already out as of yesterday's update" — corrected from a first draft that said "remains out" as if newly reported at Final. When a change (injury withdrawal, etc.) was already captured in the 24hr update, the Final tweet should note it happened earlier ("already out as of yesterday's update"/"already out since Friday"), not restate it as this stage's headline change. Net effect: the real diff basis for "what's new" is the *previous* stage that was actually published (24hr if one exists, else INITIAL) — not always INITIAL — even though the app body's own Omitted-sentence math still always diffs against INITIAL (see the 2026-09-04 update above; that part is unchanged).
